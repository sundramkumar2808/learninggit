Product 5 Core Problem Statement
• Multiple applicants request the same available room/bed. How can duplicate allocation be prevented?

By enforcing Mutual Exclusion (Mutex Lock) over the critical section: Check availability → Reserve bed → Write occupant record. When Applicant 1 locks the bed, Applicant 2 is blocked until release, at which point the bed is already occupied & duplicate booking is 100% prevented.

PRODUCT 5 CORE PROBLEM RESOLUTION

• Multiple applicants request the same available room/bed.
How can duplicate allocation be prevented?

When multiple students submit simultaneous requests for the exact same bed at the exact same millisecond, a race condition occurs. To prevent duplicate allocation, the system protects the critical section (availability check → reserve → record) using a Threading Mutex (threading.Lock()). Access is strictly serialized: the first thread reserves the bed, and all subsequent concurrent applicants immediately detect that the bed is occupied, guaranteeing 100% duplicate prevention.

📖 What Actually Happens Inside the Server

❌ Without Mutex — Race Bug

Student 1 → reads BED-1: available ✓
Student 2 → reads BED-1: available ✓
⏳ Both threads process request (DB latency)…
Student 1 → writes BED-1: occupied
Student 2 → writes BED-1: occupied 😱 overwrites!
💥 Two students share one bed — DATA CORRUPTION!

✅ With Mutex — Safe

Student 1 → lock.acquire() ✅ got it
Student 2 → lock.acquire() 🔒 BLOCKED
Student 1 → reads + writes BED-1 safely
Student 1 → lock.release()
Student 2 → unblocked → BED-1 is occupied → tries BED-2
✅ Every student gets a unique bed. Zero duplicates.
